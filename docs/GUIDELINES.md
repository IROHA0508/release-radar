## 1. 프로젝트 목표

### 목표 1. 레이더: 세 회사의 최신 소식·사용법·가격 추적 (운영 중)
- ChatGPT(OpenAI), Claude(Anthropic), Gemini(Google)의 **공식 발표**를 소식 단위로 한국어 요약한다.
- 소식마다 핵심 수치, 모델 사양, 활용 팁, 추천 프롬프트, 공식 출처를 담는다.
- 프롬프트 가이드 탭과 API 가격표 탭을 매일 공식 페이지와 대조해 최신으로 유지한다.

### 목표 2. AI 활용 기술: 정리하고 직접 해 보기 (기술 페이지 운영 중, 랩 준비 중)
- 하네스 엔지니어링, RAG, Skills(SKILL.md), AI 에이전트, MCP 서버 등 모델을 실제로 써먹는 기술을 정리한다.
- 읽고 끝나는 글이 아니라 **직접 실행해 볼 수 있는 최소 예제**까지 제공한다.
- 개념 → 원리 → 프레임워크 없이 직접 구현 → 공식 SDK로 구현 → 세 회사 비교 순서로 이해를 쌓는다.
- **기초부터 차근차근** 진행한다. 이미 아는 단계는 건너뛸 수 있도록 각 랩 첫머리에 "이 랩을 건너뛰어도 되는 경우"를 적는다.

### 목표 3. 기술 레이더: 새로 떠오르는 활용 기술 발견과 갱신 (초기 항목 운영 중, 자동 수집 준비 중)
- 내가 이름을 아는 기술 밖에서 새로 떠오르는 기술을 공식 소식에서 찾아 목록으로 관리한다(9장).
- 목록은 자동으로 후보를 모으고, 랩으로 만들지는 사람이 정한다.

### 대상 독자
- **1차 독자는 나(학습용).** 설명 깊이와 순서는 내 학습에 맞춘다.
- **링크를 받은 지인 몇 명이 2차 독자.** 따라서 다음을 지킨다.
  - 각 랩 README만 읽고도 처음부터 따라 할 수 있게 쓴다(내 컴퓨터에만 있는 경로·설정 금지).
  - 공개 저장소이므로 개인 정보, 토큰, 개인 메모는 넣지 않는다.
  - 검색 노출이 필요 없으므로 SEO·홍보 작업은 하지 않는다.

### 세 목표의 연결
- 레이더의 소식이 랩 주제에 영향을 주면 서로 링크한다(예: 새 Skills 기능 발표 → Skills 랩 페이지의 '최근 변경'에 표시).
- 랩 페이지는 레이더가 이미 쌓은 데이터(가격표, 프롬프트 가이드)를 재사용하고 중복 작성하지 않는다.
- 기술 레이더의 근거는 레이더에 올라온 '활용 팁' 소식이다.

### 하지 않는 것 (범위 밖)
- 세 회사 외 모델(오픈소스, 다른 회사)의 소식 추적. 단, 랩 실습에서 로컬 모델을 '실행 도구'로 쓰는 것은 허용.
- 루머·유출·비공식 벤치마크 정리.
- 사이트에서 사용자의 API 키를 받아 대신 호출하는 기능(보안·비용 문제).

## 2. 핵심 원칙 (모든 작업에 공통)

1. **공식 출처만.** 모든 사실·수치·가격·모델 ID는 회사의 공식 발표, 공식 문서, 공식 블로그에서 온다. 출처 URL이 없는 문장은 넣지 않는다.
2. **지어내지 않는다.** 원문에 없는 수치는 쓰지 않는다. 레이더는 `backend/guard.py`가 이를 기계적으로 검사하고, 랩 콘텐츠도 같은 기준을 따른다. 모르면 `null`이나 "공식 문서에 명시 없음"으로 둔다.
3. **한국어, 쉬운 말.** 설명은 한국어로 쓰고, 영어 용어는 처음 나올 때 한 번 원어를 병기한다(예: 검색 증강 생성(RAG)). 결론을 먼저 쓴다.
4. **원리를 먼저.** "이렇게 하면 된다"보다 "왜 이렇게 동작하는가"를 먼저 설명한다. 랩은 SDK를 쓰기 전에 핵심 루프를 직접 짜 보는 단계를 반드시 둔다.
5. **날짜를 붙인다.** AI 기능은 빨리 바뀐다. 모든 콘텐츠에 `verifiedAt`(마지막 확인일)을 두고, 오래된 내용은 화면에 표시한다.
6. **단순한 구조 유지.** 빌드 없는 정적 사이트, 데이터는 JSON 파일 하나당 항목 하나, 스키마 문서와 검증 스크립트를 통과해야만 반영한다.
7. **돈이 새지 않게.** 사이트 자동화는 Claude 구독 토큰으로 돌리고 API 과금을 쓰지 않는다. 랩 실습만 API 키로 소액 과금하며(5.6), 둘의 키는 절대 섞지 않는다. 실행당 처리 건수 상한을 둔다.
8. **비밀은 저장소 밖에.** 토큰·API 키는 GitHub Secrets나 로컬 `.env`에만 두고, `.env`는 `.gitignore`에 포함한다.
9. **망가져도 되돌릴 수 있게.** 모든 실습은 코드(git)와 환경(랩 전용 환경)을 따로 되돌릴 수 있어야 한다(6장).

## 3. 사이트 구조 (정보 구조)

```
상단 탭
├─ 새 소식        (목표 1) 모델 출시 · 모델 업데이트 · 활용 팁       #/ , #<id>
│                  회사·종류·기간(연도·월) 필터, 10건씩 보여 주고 스크롤하면 이어서 표시
├─ 프롬프트 가이드 (목표 1) 공통 원칙 · 회사별 방법 · 앱 기능 대응표   #guide
├─ API 가격표     (목표 1) 현재 가격 · 지원 종료 예정 · 가격표에 없는 모델  #prices
├─ AI 활용 기술   (목표 3) 최신 활용 기술(기술 레이더)               #tech, #tech/<id>
└─ AI 활용 LAB    (목표 2) 학습 경로 12단계, 실습은 각 단계 페이지에 붙인다  #lab, #lab/<id>
```

- 'AI 활용 기술' 탭(최신 활용 기술)과 'AI 활용 LAB' 탭(학습 경로)은 운영 중이다(2026-10-22). 두 탭 모두 `data/tech.json`을 `group`으로 나눠 쓰고, 형식은 `docs/DATA_SCHEMA.md`.
- 기술 페이지 필수 항목: **기술 이름, 정의, 왜 필요한가, 어떻게 활용하나, 기대 효과.**
- 기술 페이지 추가 항목(사용자 결정): 공식 출처 링크, 관련 소식 링크, 관련 기술 연결, 레이더 단계 표시, 짧은 예시, 한계·주의점, 난이도·선행 지식. 세 회사 지원 현황 비교는 넣지 않는다(필요해지면 랩 페이지에서).
- `tech`, `lab`은 소식 id 예약어다(`scripts/validate_data.py`, `backend/store.py`). 예전 주소 `#tech/<학습 경로 id>`도 해당 LAB 페이지로 열린다.
- 랩 화면은 학습 경로(번호 순서)를 따르고, 카드마다 예상 소요 시간, 필요한 것, 마지막 확인일, "완료" 체크(브라우저 저장, 나만 보임)를 둔다.

## 4. 목표 1 운영 지침 (레이더)

현재 구현을 기준으로 유지하되 다음을 지킨다.

- **소식 종류는 3가지만:** `모델 출시`, `모델 업데이트`, `활용 팁`. 새 종류가 필요하면 먼저 이 문서와 `docs/DATA_SCHEMA.md`를 고친다.
- **수집 주기:** 6시간마다 감지, 하루 한 번 가격표·프롬프트 가이드 점검(현행 유지).
- **품질 기준:** 소식 한 건은 `tldr` 2~3문장, 핵심 수치 3~4개, 출처 1개 이상. 그래프는 원문에 텍스트로 공개된 값만.
- **가격 표기:** 기본 등급 텍스트 토큰, 100만 토큰당 USD, 공식 페이지 문구 그대로.
- **사용법 추적 강화:** 소식에 `topics` 필드(선택)를 추가해 관련 랩·기술 레이더 항목을 태그한다. 예: `"topics": ["mcp", "compaction"]`.
- **소스 보강:** 기술 글이 많이 올라오는 Anthropic Engineering 블로그(`anthropic.com/engineering`)를 감시 소스에 명시적으로 추가하는 것을 검토한다(현재는 사이트맵을 통해 간접적으로만 잡힘).
- **실패 처리:** 자동 실행이 실패하면 `backend/state/last-run.json`과 Actions 알림에 남기고, 인증 오류는 워크플로를 실패로 표시한다(현행 유지).

## 5. 목표 2 콘텐츠 지침 (랩)

### 5.1 학습 경로 (기초부터, 번호 순서)

| 순서 | id | 주제 | 이 랩을 마치면 할 수 있는 것 |
|---|---|---|---|
| 0 | `setup` | 실습 환경 준비와 복구 연습 | 랩 전용 환경을 만들고, **일부러 망가뜨린 뒤 5분 안에 되돌리기** |
| 1 | `llm-api` | 모델 API 첫 호출 | 메시지 구조, 토큰, 비용, 스트리밍을 이해하고 세 회사 API를 한 번씩 호출 |
| 2 | `structured-output` | 구조화된 출력 | 모델 답을 JSON 스키마에 맞춰 받고 검증 |
| 3 | `tool-use` | 도구 호출(Function Calling) | 모델이 함수를 고르고 결과를 받아 답하는 한 번의 왕복을 직접 구현 |
| 4 | `agent-loop` | AI 에이전트 만들기 | 도구 호출을 반복하는 에이전트 루프를 직접 짜고, 공식 SDK로 다시 구현 |
| 5 | `context-eng` | 컨텍스트 엔지니어링 | 긴 작업에서 무엇을 남기고 버릴지(컴팩션, 캐싱, 메모리) 결정 |
| 6 | `harness` | 하네스 엔지니어링 | 에이전트를 감싸는 실행 환경(권한, 검증, 재시도, 로그, 중단 조건)을 설계 |
| 7 | `skills` | Skills(SKILL.md) 작성·조정 | 스킬을 만들고, 설명(description)을 고쳐 언제 불리는지 조정 |
| 8 | `mcp` | MCP 서버 만들기 | 내 도구를 MCP 서버로 만들어 Claude Code 등 클라이언트에 연결 |
| 9 | `rag` | RAG | 문서 분할 → 임베딩 → 검색 → 답변 파이프라인을 만들고 검색 품질을 평가 |
| 10 | `evals` | 평가(Evals) | 프롬프트·에이전트 변경이 좋아졌는지 숫자로 확인하는 작은 평가 세트 만들기 |
| 11 | `multi-agent` | 서브에이전트와 모델 섞어 쓰기 | 구현·검증을 다른 에이전트(모델)에 나눠 맡기기 |

- 순서 원칙: **앞 랩이 뒤 랩의 재료가 되게** 한다. 랩마다 `prerequisites`(선행 랩)를 적는다.
- 파일럿은 0번(`setup`)과 1번(`llm-api`)으로 한다. 이 두 개로 랩 페이지 틀과 실습 폴더 구조를 검증한 뒤 3번 이후로 넘어간다.
- 주제 추가는 기술 레이더(9장)에서 '랩' 단계로 올라온 항목만 한다.

### 5.2 랩 페이지 하나의 구성 (고정 틀)

1. **한 줄 정의**: 이 기술이 무엇인지 한 문장.
2. **건너뛰어도 되는 경우**: "아래 세 가지를 이미 할 수 있으면 다음 랩으로".
3. **왜 필요한가**: 이 기술 없이 생기는 문제를 구체적인 예로.
4. **원리**: 동작 순서를 그림(다이어그램)과 함께. 메시지가 오가는 순서, 누가 무엇을 결정하는지.
5. **직접 구현 (프레임워크 없이)**: 50~150줄 안팎의 최소 코드로 핵심만.
6. **공식 SDK로 구현**: 같은 기능을 공식 도구로. 직접 구현과 무엇이 달라졌는지 비교.
7. **세 회사 비교표**: 기능 이름, 지원 여부, 차이점, 공식 문서 링크. 확인 못 한 칸은 "확인 필요".
8. **비용**: 실습 1회에 대략 어느 정도 토큰이 드는지, 레이더의 가격표 데이터를 참조해 계산.
9. **자주 나는 오류와 해결**: 실제로 막혔던 오류 메시지와 해결 방법(실습하면서 계속 추가).
10. **더 해 보기**: 난이도를 올린 과제 2~3개.
11. **관련 소식**: 레이더에서 이 주제로 태그된 소식 자동 연결.
12. **출처와 마지막 확인일**

### 5.3 실습 코드 기준

- **위치:** `labs/<번호>-<id>/` 폴더(예: `labs/03-tool-use/`). `README.md`(실행 방법), 코드, `requirements.txt`, `.env.example`.
- **언어:** Python 기본(백엔드와 통일). MCP 등 TypeScript가 공식 예제의 중심인 주제는 TypeScript 버전을 추가로 둘 수 있다.
- **실행 환경:** 6장의 표준 환경을 따른다. 사이트(브라우저)에서 직접 API를 호출하지 않는다.
- **키 없이 해 보는 길:** 각 랩에 API 키 없이 확인할 수 있는 단계를 둔다(가짜 모델 응답으로 구조만 확인하는 `--dry-run` 모드 등).
- **비용 상한:** 기본 모델은 작은 모델, 최대 반복 횟수와 토큰 상한을 코드 맨 위 상수로 명시한다.
- **실행 검증:** 모든 랩 코드는 오프라인 테스트(모델 호출을 가짜로 대체)로 CI에서 돌아가야 한다. 실제 API 호출 테스트는 수동 실행으로만.
- **코드 스타일:** 주석과 출력 메시지는 한국어, 변수·함수 이름은 영어.

### 5.4 랩 데이터 형식 (랩 0 작성 시 확정)

기술 설명(정의·필요성·활용·효과)은 이미 `data/tech.json`에 있으므로 랩 데이터에는 **실습 내용만** 둔다. `data/lab/<id>.json` 하나에 랩 하나, id는 `data/tech.json`의 학습 경로 id와 같게 한다. 아래는 초안이며 랩 0을 만들면서 확정한다.

```json
{
  "id": "tool-use",
  "order": 3,
  "minutes": 60,
  "skipIf": ["...", "..."],
  "needs": ["6장 표준 환경", "API 키 1개 또는 --dry-run"],
  "sections": [{ "key": "why", "title": "왜 필요한가", "body": "..." }],
  "compare": [{ "feature": "...", "openai": {}, "anthropic": {}, "google": {} }],
  "code": { "path": "labs/03-tool-use", "entry": "main.py" },
  "errors": [{ "message": "...", "cause": "...", "fix": "..." }],
  "sources": [{ "title": "...", "url": "https://..." }],
  "watch": [{ "title": "...", "url": "https://...", "hash": "(자동)" }],
  "verifiedAt": "2026-10-21"
}
```

- 형식이 정해지면 `docs/DATA_SCHEMA.md`에 추가하고 `scripts/validate_data.py`에 검사를 넣은 다음에 콘텐츠를 쓴다.
- `watch`는 프롬프트 가이드와 같은 방식으로 매일 공식 문서 변경을 감지하는 데 쓴다.

### 5.6 랩의 모델 호출 방식 (결정)

- **API 키를 직접 쓰고 소액 과금을 감수한다.** 쓰는 회사는 **OpenAI와 Anthropic 두 곳**. Google은 비교표에만 넣고, 필요해지면 나중에 추가한다.
- **모든 랩 코드는 두 회사를 바꿔 끼울 수 있게 쓴다.** `.env`의 `LAB_PROVIDER=openai` 또는 `anthropic` 한 줄로 전환한다. 같은 일을 두 API로 해 보면서 요청·응답 구조 차이를 보는 것 자체를 학습 내용으로 삼는다(각 랩의 '세 회사 비교표'와 연결).
- **기본 모델은 각 회사의 가장 싼 텍스트 모델**로 하고, 랩 README에 "더 큰 모델로 바꿔 볼 때"를 따로 적는다.

| 회사 | 기본 모델 (API ID) | 입력 / 출력 (100만 토큰당) | 올려 볼 모델 |
|---|---|---|---|
| OpenAI | GPT-6 Luna (`gpt-6-luna`) | $0.10 / $0.50 | GPT-6.1 Sol (`gpt-6.1-sol`) $2 / $10 |
| Anthropic | Claude Haiku 5.5 (`claude-haiku-5-5`) | $0.10 / $0.50 | Claude Sonnet 5.5 (`claude-sonnet-5-5`) $2 / $10 |

> 가격은 사이트 API 가격표(`data/prices.json`, 2026-10-21 12:30 확인) 기준. Haiku 5.5는 10만 토큰이 넘는 프롬프트에 더 높은 가격이 붙는다. 랩 코드는 모델 ID를 하드코딩하지 말고 `.env`에서 읽으며, 랩 페이지의 가격은 가격표 데이터를 참조해 자동으로 맞춘다.

- **대략적인 비용 감각(기본 모델 기준):** 호출 20번, 매번 입력 2천 토큰·출력 500토큰이면 입력 4만 + 출력 1만 토큰 = 약 $0.01. 에이전트 루프처럼 대화가 길어져 이 10배가 돼도 약 $0.1. 한 회사에 $5만 충전해도 기초 경로(랩 0~4)는 충분히 반복할 수 있다.

### 5.7 랩 작성 방식 (결정: 대화하며 함께 작성)

랩의 1차 목적은 내가 익히는 것이므로, **쓰는 과정 자체를 학습으로** 삼는다. 완전 자동 생성은 쓰지 않는다.

1. **초안:** 프로젝트 대화에서 Claude가 랩 페이지 초안과 코드를 쓴다(공식 문서 확인 후, 출처 포함).
2. **실행:** 내가 표준 환경(6장)에서 직접 실행한다. 원리 설명이 이해되지 않으면 그 자리에서 질문하고, 답을 본문에 반영한다.
3. **오류 기록:** 실행 중 난 오류는 원인·해결과 함께 '자주 나는 오류'(`errors`)에 기록한다.
4. **반영:** 실행이 끝까지 통과한 코드만 커밋한다. 랩 페이지의 `verifiedAt`은 내가 실행한 날짜로 한다.

- 갱신: 공식 문서 변경이 감지되면(5.8) 같은 방식으로 다시 실행해 보고 고친다.
- 이 방식은 랩 0·1을 만든 뒤 다시 평가한다(랩 하나에 드는 시간, 남는 것). 필요하면 갱신만 '자동 초안 + 검수(PR)' 방식으로 바꾸는 것을 검토한다.

### 5.8 최신성 관리
- 랩 페이지의 근거 문서(`watch`)가 바뀌면 "변경 감지됨" 표시를 띄우고 사람이 확인한다. 초기에는 **자동 수정하지 않고 알림만** 한다(코드가 섞여 있어 자동 수정 위험이 큼).
- `verifiedAt`이 90일을 넘으면 화면에 "오래된 내용일 수 있음"을 표시한다.

### 6.2 결정: 표준 환경
- **표준은 A(VS Code + WSL2 + 랩 전용 환경).** 이미 갖춘 환경이고, MCP·Skills처럼 내 Claude 앱과 연결해야 하는 랩에 가장 자연스럽다.
- **저장소에 `.devcontainer/devcontainer.json`도 함께 둔다.** 그러면 A가 꼬였을 때 C(Codespaces)로 바로 갈아탈 수 있고, 링크를 받은 지인도 설치 없이 같은 환경을 연다. B는 필요해질 때 쓴다.
- **D(Colab)는 보조.** GPU가 필요한 일부 실험에만 노트북을 따로 제공한다.

### 6.3 오류가 나도 되돌릴 수 있게 하는 안전망 5가지
1. **코드: git.** 실습 시작 전 커밋하고, 실험은 브랜치에서. 망가지면 `git restore .`(마지막 커밋으로) 또는 `git stash`(잠시 치워 두기).
2. **환경: 랩 전용 환경 하나만 쓰고, 그 밖은 건드리지 않는다.** 기존 딥러닝용 conda 환경과 분리된 `rr-labs` 환경을 만든다. 시스템 PATH 수정, 전역 `pip install`, `sudo pip`는 금지. 환경이 꼬이면 통째로 지우고 다시 만든다(몇 분이면 됨).
3. **비용: 상한을 먼저.** 두 회사 모두 선불 크레딧 방식이라 충전한 만큼만 쓰인다. 단, 다음을 지킨다.
   - **OpenAI:** 결제 설정 시 자동 충전(auto recharge)이 기본으로 켜지므로 **반드시 끈다**. 잔액이 0이 되는 순간 바로 멈추지 않아 약간 마이너스가 될 수 있다(다음 충전에서 차감). 남은 크레딧의 만료일(구매 후 1년)을 확인해 먼저 쓴다.
   - **Anthropic:** Claude Console에서 크레딧을 산다(환불 불가, 구매 후 1년 만료). 자동 충전(auto-reload)은 설정하지 않는다. 크레딧이 떨어지면 API 호출이 멈춘다.
   - 코드에는 최대 반복 횟수·최대 출력 토큰을 상수로 두고, 실행이 끝날 때마다 사용한 토큰 수와 예상 비용을 출력한다.
   - Codespaces는 결제 수단을 등록하지 않는다.
4. **비밀: `.env` + `.gitignore`, 키는 용도별로.** 랩용 키는 이름을 `rr-labs-local`처럼 붙여 따로 발급하고, 사이트 자동화(GitHub Secrets)에는 절대 넣지 않는다. 키가 커밋되거나 노출되면 즉시 콘솔에서 폐기하고 새로 발급한다(지우는 것만으로는 부족).
5. **막혔을 때: 세 가지를 붙여서 물어보기.** ① 에러 전문 ② 실행한 명령 ③ `which python`·`python --version` 결과. VS Code의 Claude Code에 그대로 붙여 넣는다. 해결되면 그 랩의 '자주 나는 오류'에 기록한다.

> 랩 0(`setup`)에서는 이 다섯 가지를 **직접 해 본다**: 환경을 만들고, 일부러 패키지를 꼬이게 한 뒤 지우고 재생성하고, 코드를 망가뜨린 뒤 git으로 되돌린다. "망가져도 되돌릴 수 있다"는 경험을 먼저 하는 것이 목적이다.

- 커밋 메시지는 한국어로 무엇을 왜 바꿨는지 쓴다.
- 커밋 작성자 이메일은 저장소 주인의 GitHub 계정 이메일로 한다(커밋이 GitHub 계정에 연결되도록).

- 자동 생성 콘텐츠(`release-radar-bot` 커밋)와 사람이 쓴 콘텐츠를 섞어 고칠 때는 자동 실행과 충돌하지 않도록 `main`에 바로 푸시하지 않는다.
- 공식 문서를 확인하지 못한 내용은 쓰지 말고 "확인 필요"로 남긴 뒤 보고한다.
- 실습을 도울 때는 답만 고쳐 주지 말고 **왜 그 오류가 났는지** 먼저 설명한다.

### 9.2 자동 갱신 방식 (제안)
- 레이더 파이프라인이 '활용 팁' 소식을 요약할 때, Claude가 소식에서 **기술 이름**을 함께 뽑는다.

- 데이터: `data/tech.json`의 `group: "radar"` 항목. 근거는 `news`(소식 id), 처음·최근 언급 날짜는 화면에서 그 소식 날짜로 계산한다. 자동 후보는 바로 반영하지 않고 후보 목록으로 남겨 사람이 정의·출처를 확인한 뒤 추가한다.
